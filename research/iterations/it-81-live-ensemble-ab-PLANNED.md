# ИТЕРАЦИЯ 81 (PLANNED) — Живой A/B ансамбля old⊕new в конвейере (перенос контурных рядов it-75)

- **Дата:** 2026-09-22. Предрегистрация ДО кода, прогона и любых чисел.
- **Источник:** it-74/75 (офлайн-ряды AND/OR), it-68 (протокол живого A/B v5), SYNTHESIS-ensemble
  («подтверждение на живом контуре — открытый вопрос»).
- **Гипотеза:** ансамбль old⊕new как функция решения в видео-ветке боевого конвейера
  (Kafka-пайплайн, живой источник, watermark k=5, τ=0,5) **воспроизводит направление офлайн-
  предсказания it-75 на том же материале**: OR(max@0,40) не хуже одиночного old (офлайн +0,004
  F1), AND(min@0,40) на этом контуре проигрывает по реколлу (офлайн −0,019 F1), а цена ×2
  инференса на GPU не ломает оперативность.

## Почему это решает вопрос

Офлайн-пара 94,7/7,2 (it-74) — image-ряд смешанного режима; контурная заявка — за живым
прогоном (вердикт it-74: «экспорт-заявка требует живого A/B (аналог it-68)»). Офлайн на
sandbox-контуре уже предсказывает исход по рядам it-75: `old F1 0,961 / AND 0,942 / OR 0,965`.
Живой контур добавляет аудио-ветку и агрегацию окон — переносится ли направление — вопрос
замера, не веры.

## Реализация (минимальная, в контракте it-67)

`YoloDetector` получает опции (через стандартные env-переопределения `UAVDET_VISUAL_DETECTOR__*`):
`vote_weights_path`, `vote_mode ∈ {off, and, or}` (по умолчанию `off` — поставка не меняется),
`vote_floor` (0,4). Семантика ровно как в каноне it-74/75 на по-кадровом `max_conf`:
- **and**: кадр выдаёт детекции primary только если `maxA ≥ floor` и `maxB ≥ floor`
  (иначе — пустая детекция, т.е. штатный non-drone-путь консьюмера);
- **or**: кадр положителен при `max(maxA, maxB) ≥ floor`; выдаются детекции модели с бо́льшим
  max (p_v окна = max по кадрам — согласуется с OR-рядом it-75);
- voter — вторая модель (new, `best.pt` it-65, sha `7042602a…`), копируется в `models/visual/`
  (в git не входит); `model_name` = `old+voted` → provenance решений фиксирует состав (it-67).
- unit-тесты на фиктивной модели (паттерн `test_sahi.py`: `__new__` + подставные детекции),
  полный `make test` зелёный до живого прогона.

## Протокол прогона (v5-каркас it-46/68, GPU docker)

`research/it81_ab_run.sh` (создаётся до прогона, коммитится с предрегистрацией): 3 этапа × 240 с,
`score_stages.py --burn-in-s 90`, скоринг по `media_ts` (фаза не подбирается), веса —
постоянные обеих плеч; override fusion — боевой `watermark`+k=5+τ=0,5 (как в поставке после it-68)
во всех этапах; различаются только env видео-ветки:
- **A (baseline):** `vote_mode=off` (одиночный old, `yolov8s-uav.pt` sha `41f3fd55…`);
- **B (AND):** `vote_mode=and`, floor 0,4, voter=new;
- **C (OR):** `vote_mode=or`, floor 0,4, voter=new.
Порядок A→B→C фиксирован; стек GPU-composes (`docker-compose.gpu.yml`), после прогона — явный
`pipeline-down`/`infra-down` с сохранением jsonl (ритуал it-68 п. 5).

**Operational-заметка (22.09, ДО первых замеров):** холостой пуск runner'а выявил пустой прогон —
Kafka в этом стеке без auto-create, а топики (`video.raw/audio.raw/inference/decisions`) создаются
отдельной командой `make topics-create`, которой в каркасе v5 не было (в тех же холостых условиях
v5 полагался на уже созданные вручную). Этапы не засчитаны (inference=0, решений нет, измерений не
было). Правка runner'а до боевого пуска: (1) `create_topics()` с проверкой `--list` и отказом при
отсутствии топика; (2) ранний стрим-гейт в `stage()` — через 25 с после `up` счётчик
`uavdet.inference` обязан быть > 0, иначе abort (не давать 240 с пустому этапу). Критерии P0–P5 не
меняются.

### Аудит-находка ДО прогона (22.09): механизм per-stage override в v3/v5 был мёртвый

При разборе каркаса выяснено: `ablation_v3/v5.sh` пишут `infra/docker-compose.it4x.yml`, но в
массиве `COMPOSE` нет `-f "$OVR"` (в v2 — было; при `--file` автоподхват override отключён).
Следствие: все этапы живых прогонов it-43/46/68 крутились на ОДНОЙ конфигурации pilot.yaml —
межэтапные различия (F1 ±0,013; медианы A 1959/B 2414/C 1979 мс) неатрибутируемы конфигу
(шум прогонов), а «ничья F1» it-68 — ничья идентичных конфигов. Для it-81 это меняет ровно два:
(1) runner it-81 передаёт `-f "$OVR"` явно; (2) каждый этап обязан ДО измерений подтвердить
проникновение env в контейнер (`docker exec uavdet-visual-detector env | grep UAVDET_VISUAL`) —
иначе этап не засчитывается. Ожидание P0 (F1(A) ≈ 0,967) переосмыслено: это фактическое число
it-68 на реально действовавшей там конфигурации watermark/k=5 из pilot.yaml — то есть базовая
точка боевой поставки, что нам и нужно. Атрибуция it-43/46 как «сравнений конфигураций»
подлежит отдельной ревизии (фиксируется в SYNTHESIS/REPORT-DELTA как кандидат поправок).

## Предрегистрированные критерии (фиксируются ДО прогона, 22.09.2026)

Метрика — основной вывод `score_stages.py`: NORM, стационар (burn-in 90 с), F1 vs presence-GT;
плюс медиана `e2e_latency_ms` по интервалам `SCORE_OFF` (обкатанный конвейер it-68 U3).
- **P0 (блокататор harness'а):** NORM-F1 этапа A ∈ [0,957; 0,977] (ожидание ≈ 0,967 как в it-68;
  допуск ±0,01). Красный ⇒ прогоновая среда дрейфует, вердикты B/C не выносятся.
- **P1 (перенос направления AND):** F1(B) ≤ F1(A) + 0,005 и R(B) ≤ R(A) (офлайн-предсказание:
  AND режет реколл на airborne-границах, FN 5→6 it-74 G4). AND-лучше-A более чем на 0,01 ⇒
  необъяснённое расхождение — итерация не закрывается без разбора.
- **P2 (перенос направления OR):** F1(C) ≥ F1(A) − 0,002 и R(C) ≥ R(A) (офлайн: 0,965/1,000 vs
  0,961/0,991). Красный ⇒ живой перенос OR-ряда отрицателен — регистрируется честно.
- **P3 (цена ×2):** медиана e2e B и C ≤ A + 1,0 с (порог как в it-68 U3; GPU-инференс, ожидание ~мс).
- **P4 (provenance/документирование):** в `decisions.jsonl` этапов B/C имя модели содержит
  состав ансамбля (grep по `models`), артефакт `it81_ab_summary.txt` (sha весов, SCORE_OFF, строка
  реестра) — ключ манифеста; блоки REPRODUCE и сноски README/models — как в it-68 U4.
- **P5 (засчитанность этапов):** для каждого этапа B/C — вывод `docker exec … env | grep
  UAVDET_VISUAL` с ожидаемыми значениями vote-переменных зафиксирован в логе прогона ДО скоринга;
  отсутствие/расхождение ⇒ этап не засчитывается (следствие аудит-находки про мёртвый OVR v3/v5).

## Риски/рамки

- Материал — sandbox-сессия (72,6 с клип, циклический источник): FP-окна here — стоящий дрон
  (presence-семантика, it-66), поэтому AND на этом контуре выигрывать не должен — это часть
  предсказания, а не дефект. Разделение «фон vs дрон» для FP-оси — роль офлайн E1 (it-74), не живого A/B.
- 1 тест-материал, независимости нет: A/B подтверждает перенос функции решения в конвейер,
  не универсальность профиля (рамка SYNTHESIS остаётся).
- Нагрузка: GPU-docker + симулятор; запуск только при пустых цепочках и доступном GPU
  (`docker info` nvidia), память ≥2 ГиБ; чужие контейнеры не трогать.
- `pilot.yaml` не правится (vote по умолчанию off); поставка меняется только если автор решит
  после вердикта.
