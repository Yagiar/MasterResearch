# it-87 — frozen final holdout · ПРЕДРЕГИСТРАЦИЯ (протокол до открытия материала)

Дата предрегистрации: 2026-09-24. Приоритет P1-финал роадмапа (`DECISION-roadmap-post-it82.md`):
единственный подтверждающий (confirmatory) замер цикла; после него — стоп экспериментов.
Статус: **блок — материал** (новый cam+mic синхронный материал от автора; цикл не может его
сгенерировать). Прогон — на GPU-пайплайне, строго после it-85/it-88.

## Смысл

Все it-01…86 — development/exploratory evidence (адаптивное переиспользование материалов
запрещено стоп-критерием). it-87 — одна предваряемая проверка боевой линейки
(`AND_presence_live` + fusion-контур) на материале, который цикл **никогда не видел**:
открытие однократное, вердикт по предрегистрированным гейтам, красный результат не триггерит
новый τ/новую политику.

## Гейты вердикта (предрегистрированы; односторонние, без «подкрутим после»)

- **H0 (блокаторы, до вердиктов):** sha весов совпали; материал новый (пути/хэши не пересекают
  it-01…86 входы); аудио-телеметрия живая (урок it-30/гейт M0 it-86): при включённом аудио
  audio-инференсы присутствуют; `media_ts` ratio ∈ [0,8; 1,2] на каждом сегменте (гейт S1 it-83);
  цельность записи по media_ts (уточнение пре-открыточного аудита 24.09: монотонность по порядку
  потока внутри модальных подпотоков trigger_modality — глобальная монотонность конструктивно
  невозможна в двухчасовом merge-адаптере, см. секцию аудита ниже).
  Любой H0-провал → прогон чинится и повторяется, вердиктов не существует.
- **H1 (ложные тревоги, негативы):** доля alarm-окон контура на бездронных сегментах ≤ **15 %**
  (якорь: пофреймовый paired-канон it-84 FP(B)=10,5 % на HD-фонах; 15 % — верхняя граница
  подтверждения на новом материале; строго односторонний).
- **H2 (поймал ли, позитивы):** sequence-level recall ≥ **90 %** пролётов (в пролёте ≥1 alarm-окно
  внутри помеченных границ) при n≥5.
- **H3 (скорость, TTD):** медиана TTD (граница «дрон виден» → первый alarm) ≤ **10 с**, p90 ≤ **20 с**.

## Вердикт-правило

«Подтверждено» := H0 ∧ H1 ∧ H2 ∧ H3 на однократном открытии. Любой красный — честная фиксация
(синтез/отчёт переписываются под фактическое число; политика не меняется, τ не ищется заново —
стоп-критерий). После it-87 эксперименты только для блокер/багов.

### Пре-открыточный аудит runner'а (24.09, починки обвязки, не замер)

Ручной проход `it87_holdout_run.sh` перед единственно допустимым боевым пуском нашёл три
дефекта «молча испорченного однократного замера» (перезапуск сегмента после боевого пуска
запрещён протоколом — значит runner обязан ОТКАЗЫВАТЬ, а не продолжать с грязным срезом):

1. **CRLF-манифест**: `read` из файла записи автора мог утащить `\r` в поля `dur/ge`
   (поломка awk-арифметики таймеров) → чтение через `tr -d '\r'`.
2. **Таймаут дренажа без вердикта**: выход из цикла `DEADLINE` при `STABLE<45` продолжал прогон
   с обрезанным срезом → жёсткий ОТКАЗ (обрезанный срез = тихая порча H1/H2 однократного замера).
3. **Нет нижней границы длительности**: сегмент `dur<20` даёт `exp=dur−10≤0` и NaN-ratio в eval
   → гейт `dur≥20` на входе этапа.
4. **P5-гейты на «или»**: `grep -E "A|B"` пропускал полу-конфигурацию (например `VOTE_MODE=and`
   без `VOTE_FLOOR=0.40`) → оба гейта (vote и source) переписаны на конъюнкцию двух
   `grep -qE`; логика проверена: частичный env отвергается, полный проходит.
5. **Отказ посреди прогона из-за манифеста**: отсутствующий файл/кавычка в имени/нарушение спеки
   (pos<5, негативы<600с) всплывали только на этапе стадии, когда однократный замер уже испорчен
   → добавлен up-front проход манифеста ДО всякого docker-пуска (существование видео/аудио в
   песочнице, запрет `"` в именах, счётчики спеки); позитивно/негативно протестировано
   (полный манифест → OK; 4 pos → отказ; негатив 300с → отказ; нет neg1.wav → отказ).
6. **Мусорная роль съедала сегмент молча**: up-front счётчик пропускал `role∉{pos,neg}`
   (например `позитив`/`poz` — опечатка автора), eval включал такой сегмент в полноту H0,
   но он не попадал ни в H1, ни в H2 → однократный прогон тратился без вердиктного учёта.
   Теперь: ОТКАЗ в up-front обоих раннеров (it87, it86-full) + assert в `load_manifest`
   eval (вторая линия). Проверено живьём: `позитив`→отказ, `poz` на второй строке→отказ,
   валидный манифест 5 pos+700с neg → OK (после greп-захвата убит timeout'ом; leftover
   overlay удалён), eval-assert сработал.

Измерительный стек (веса/τ/режим/гейты H0–H3) не тронут — только отказные условия обвязки;
`bash -n` чист, гейт dur проверен (25/20→OK; 19,9/abc→FAIL), манифест пересобран (149, OK).

### Пре-открыточный аудит eval (24.09, починки харнеса разбора, не замер)

Проход `it87_holdout_eval.py` перед боевым открытием нашёл два дефекта в самих блокаторах:

1. **Ваккуумный гейт media_ts-monotonic**: `mm.sort()` исполнялся ДО проверки монотонности —
   отсортированный ряд монотонен тривиально, т.е. H0-блокатор не мог сработать никогда
   (при не-монотонном релизе замер был бы допущен к вердиктам). Правка: монотонность читается
   по ПОРЯДКУ ПОТОКА (jsonl), сортировка — только для дальнейшей арифметики TTD/span.
2. **p90 не по предрегистрированной формуле**: `round(0,9n)` (banker's rounding) при n=5 даёт
   4-й ряд вместо 5-го (max), т.е. гейт H3 слабел ровно при минимально допустимом n позитивов
   (спека pos≥5). Правка: nearest-rank `ceil(0,9n)`-й ряд, как зафиксировано в формулировке
   «p90 conservatism в сторону max-ряда».
3. **Аттестация расширена** (`it87_eval_selftest.py`, сценарии B/C поверх прежнего A):
   B — 5 пролётов TTD [1,2,3,4,58] → медиана 3,0/п90 58,0 → H3 🔴 (max-ряд пойман);
   C — перестановка двух окон в потоке bpos1 → `mono=ПРОВАЛ` → H0 блокирует, вердикты H1–H3
   не печатаются. A (прежний) — без изменений, зелёный.
   Формулировки H0–H3, пороги и веса не тронуты — исправлены только механизмы гейтов.

   при неполноте.
3. **Побочная находка:** строка заголовков в манифесте честно отвергается pre-flight
   («поле 'duration_s' не число») — формат TEMPLATE (комментарии `#` + данные, без шапки)
   задокументирован в самом TEMPLATE.

Формулировки H0–H3, пороги, веса и замороженный eval не тронуты — исправлены только
механизмы допуска к замеру (за исключением H0.3: её формулировка исправлена ниже как
дефект самой проверки, обнаруженный единственным живым смоуком). Смоук-песочница `smoke18`
— синтетика ffmpeg, к бою отношения не имеет, после валидации удаляется.

### Пре-открыточный аудит: media_ts-монотонность под двухчасовым слиянием (вечер 24.09, правка харнеса, не замер)

Полный смоук боевого раннера на smoke18 (шовы 18+19, 7/7 SCORE_OFF, rc=0) дал
**mono=ПРОВАЛ на всех 7 сегментах** (pos1: 33/113 инверсий, neg2: 572/1221). Диагностика
по decisions.jsonl + Postgres-инференсам: в merge-адаптере аудио-конвейер идёт быстрее
видео-конвейера (двухмодельный AND@0,40 на 1660 Ti не успевает за медиатаймлайном), аудио-
триггеры max_wait-выпуска выходят **между** видео-окнами с опережающим media_ts (лаг нарастает
до 7–14 с к 300-му секунде); глобальный ряд media_ts по порядку потока не монотонен
**конструктивно**, на 25–50 % переходов, причём каждый модальный подпоток монотонен.
smoke87 (72,6 с, одно сегментное окно) это не показал: лаг не успел накопиться. Боевые
сегменты (neg ≥ 600 с) гарантированно убили бы H0.3 — однократное открытие было бы
испорчено проверкой, которая не может пройти. Это дефект формулировки гейта (и наблюдаемости
контракта), а не материала: цель H0.3 — цельность записи (сшивка чужого этапа/повтор
материала дают откат часов), а не порядок слияния модальностей в kafka.

Правки (все — до боевого открытия, пороги H0.1/2/4, H1–H3 не тронуты):
1. `libs/common` DecisionMsg: аддитивное поле `trigger_modality` (прецедент it-67 `models`);
   fusion `_emit` пишет модальность триггера выпуска. Контракт/`schema_ver` совместимы,
   sink-JSON получает поле автоматически.
2. `it87_holdout_eval.py` H0.3: монотонность media_ts по порядку потока **внутри каждого
   подпотока trigger_modality** (video/audio; строки без поля — подсрез None, прежняя
   глобальная семантика — самопроверки A/C на ней не сломались).
3. Раннер: этапная аттестация P6b — в срезе обязано присутствовать `"trigger_modality":
   "video"`, иначе ОТКАЗ P6b (дрейф образов: без поля eval слеп к подпотокам).
4. `it87_eval_selftest.py`: сценарий D — синтетический двухчасовой интерливинг (аудио +4 с
   впереди, подпотоки монотонны, глобальный ряд с инверсиями на каждом втором переходе)
   обязан проходить H0.3; сценарий C (перестановка внутри подпотока None) по-прежнему
   блокируется. A/B/C/D зелёные.
5. Живая валидация: перезапуск смоука на том же smoke18 (смоук-материал — не боевой замер,
   повтор разрешён протоколом обвязки) — ожидания: P6b проходит, H0.3=OK по подпотокам на
   всех сегментах, при прежних инверсиях глобального ряда (сам интерливинг не чиним: менять
   пейсинг симулятора/fusion = менять измеряемую систему, канон цикла it-30…82 собран на ней).
   ИТОГ (24.09, вечерний заезд, rc=0): 7/7 SCORE_OFF; P6b пройден; все строки прогона
   размечены (video 232 / audio 228 / null=0 на pos-срезе); mono(по подпотокам)=OK на всех
   7 сегментах (при инверсиях глобального ряда: pos1 — 33, neg2 — 572/1221); единственная
   осечка H0 — ratio 1,376 на 30-с pos, ровно артефакт шва 21. После реализации гейта
   живо проверены обе ветки: ОТКАЗ pre-flight на 65-с при MIN_DUR=75 и отказ боевого
   стража при MIN_DUR=40 (до tee/docker, логи не тронуты); pos-материал smoke18
   перегенерирован на 65 с (dur в смоук-манифесте 30→65; gt 5–25 в пределах).

Побочная фиксация (и её закрытие — шов 21): pos-ratio 1,376 на 30-с смоук-сегментах — артефакт
коротких сегментов (фактический хвост ~2 с при консервативном вычитаемом 10 с: (dur−2)/(dur−10)
растёт ниже dur≈50 с). Первоначальная мысль «к бою не относится» была неверна: neg≥600 с
суммарно, но позитивы нормировались только количеством (≥5), и короткий pos-клип автора
повторил бы ложный H0.4-блок уже после необратимого замера. Закрыто допуском, а не порогом:
pre-flight `MIN_DUR=60` на каждый сегмент (боевой режим фиксирует 60 механически, по образцу
стража шва 17); пороги H0.4 (и любых других гейтов) не тронуты.
